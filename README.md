# Pose Web · 电梯场景视觉行为分析

同一个题目的两代实现，放在同一个仓库里，可以直接对照两代之间的演进。

| | [`v1-image`](v1-image/) | [`v2-elevator-guard`](v2-elevator-guard/) |
|---|---|---|
| **定位** | 图片单帧姿态检测，轻量快速 | 电梯轿厢危险行为预警，完整产品链路 |
| **输入** | 仅图片（JPG / PNG / WEBP） | 图片 + 视频 |
| **姿态模型** | 固定 YOLO11n-Pose | YOLO11n-Pose / 自训练 MEC-Pose **可切换** |
| **行为识别** | 无 | 规则引擎（六种电梯行为）/ 大模型 / PCG-GCN **可切换** |
| **危险行为** | — | 摔倒、打架、踢门、推门、扒门、靠门 |
| **门区域标定** | — | 支持，且四条门相关规则强依赖它 |
| **可视化产出** | 一张带骨架的图片 | 带骨架的**完整视频**（浏览器可直接播放）+ 关键帧 |
| **处置建议** | 单一来源 | 模板 / 大模型 / 大模型+知识库 **可对比** |
| **知识库检索** | — | 内置 BM25，可选 Chroma 向量检索 |
| **报告** | 网页文案 | 可下载的 PDF（含证据链、风险因子、知识库引用） |
| **数据库** | 无 | SQLite（含历史数据迁移） |
| **记录管理** | 无 | 筛选 / 分页 / 归档 / 批量删除 / 保留策略 |
| **典型耗时** | 约 3 秒 | 约 30 秒（14 秒 1080p 视频，含视频可视化） |
| **依赖权重** | 自动下载 | 通用权重自动下载；自训练模型为可选项 |

## 该用哪一个

**只要快速看一张图的关键点** → 用 `v1-image`。三条命令起服务，3 秒出结果，
不需要数据库、不需要标定、不依赖任何本地产物。

**要做电梯场景的危险行为预警** → 用 `v2-elevator-guard`。它覆盖了六种行为、
能出可视化视频和 PDF 报告、有记录管理，也把每个环节做成了可替换的引擎。

## 快速开始

两代各自独立，互不依赖，分别进入对应目录按各自的 README 操作。

### v1-image

```powershell
cd v1-image
Copy-Item .env.example .env      # 可选：填 LLM 配置
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r requirements.txt
uvicorn backend.app.main:app --reload
```

打开 <http://127.0.0.1:8000>。

### v2-elevator-guard

```powershell
cd v2-elevator-guard
Copy-Item .env.example backend\.env      # 可选
.\run.ps1                                 # 默认 http://127.0.0.1:8001
```

也可以直接用 Docker：

```powershell
docker compose up --build
```

详细说明见 [v2-elevator-guard/README.md](v2-elevator-guard/README.md)，
模型权重的配置见 [v2-elevator-guard/MODELS.md](v2-elevator-guard/MODELS.md)。

## 两代之间发生了什么

### 1. 从"单帧"到"时序"

v1 只处理静态图片，能给出的结论天然受限——单张二维姿态无法判断动作过程。
v2 引入视频解码、逐帧推理、轨迹跟踪和时序特征提取，
"重心在 1.2 秒内下降了多少"这类判断才成为可能。

### 2. 从"通用姿态"到"电梯场景"

v1 的输出是通用的关键点可视化。v2 把关注点收敛到电梯轿厢的六种危险行为，
并引入了一个 v1 完全没有的概念：**门区域**。

「踢门 / 推门 / 扒门 / 靠门」四类行为的共性是"人对门做了什么"，
但关键点里没有"门"这个对象——骨架只有人。不告诉系统门在哪，
这四条规则就只能瞎猜。v2 因此把门区域做成一个显式的、需要使用者标定的参数，
并且在未标定时**让这四条规则直接不参与判定**，而不是拿一个猜的默认值去产生误报。

开发过程中用一个覆盖画面 54% 的"默认区域"试过：一个只是站在电梯口按按钮的人，
被判成「踢门 0.92」和「扒门 0.99」——因为他的手脚本来就落在那个巨大的区域内。
这个教训直接决定了 v2 的默认值是"留空"。

### 3. 从"写死的流程"到"可插拔的引擎"

v1 的姿态模型写死在代码里。v2 把链路拆成三个可替换的环节：

```
姿态估计   yolo11n | mec
行为识别   none | rule | llm | stgcn
建议生成   template | llm | rag
```

编排层只认接口不认实现，所以换模型、临时关掉行为识别、
或者把 PCG-GCN 在微调后启用，都不需要改流程代码。

### 4. 修掉的那些 bug

两代开发过程中踩到并修掉的坑，都留了记录：

| 问题 | 表现 | 根因 |
|---|---|---|
| 上传被拒 | `413 图片不能超过 0 MB` | `MAX_UPLOAD_MB=0` 约定为"不限制"，代码却直接拿 0 比较 |
| LLM 静默失效 | 配了 Key 仍显示"本地规则" | 模型把 `limitations` 返回成数组，schema 要求字符串，校验失败的异常被 `except: pass` 吞掉 |
| 模型名不匹配 | 同上，但更快 | 端点只提供 Qwen 模型，配置里却填了 `gpt-4.1-mini`，返回 404 后被静默兜底 |
| 可视化视频打不开 | `<video>` 黑屏 | OpenCV 缺 `openh264`，`avc1` 写出来是 0 字节空文件却报告成功 |
| 编码太慢 | 14 秒视频导出要 108 秒 | VP9 约 257ms/帧，VP8 只要 24ms/帧，播放体验无差别 |
| 摔倒检测不到 | 快速动作漏检 | 纯 IoU 跟踪把快速位移拆成两条轨迹，"下降过程"被切掉 |
| 踢门误报 | 静止站立被判踢门 | 只用了脚速和距门距离，缺少"腿真的抬起来"这个条件 |

这些修复的具体过程写在各自的 README 里，v1 的在
[v1-image/README.md#更新记录](v1-image/README.md)，v2 的在
[v2-elevator-guard/README.md](v2-elevator-guard/README.md)。

## 仓库结构

```text
pose-web/
├─ README.md                 本文件：两代对照
├─ v1-image/                 第一代：图片姿态检测
│  ├─ backend/app/            FastAPI + YOLO-Pose
│  ├─ frontend/               单页网页
│  └─ README.md
└─ v2-elevator-guard/        第二代：电梯危险行为预警
   ├─ backend/app/engines/    可插拔引擎
   ├─ backend/knowledge/      电梯安全知识库语料
   ├─ backend/tests/          29 个单元测试
   ├─ backend/app/static/     单页网页
   ├─ MODELS.md               权重配置说明
   ├─ Dockerfile / docker-compose.yml
   ├─ run.ps1
   └─ README.md
```

两代各带自己的 `.gitignore`、`.env.example` 和启动方式，互不影响。

## 说明

- 两代都不包含任何模型权重。v2 的默认姿态模型会自动下载；
  v1 与 v2 都支持注入自训练权重，配置方式见各自的说明。
- 知识库为通用电梯乘用安全语料，**不替代正式国家标准文本**，引用前请核对现行规程。
- 系统输出仅作为安全管理辅助依据，**高风险结论须经人工确认后执行处置**。
